# PostgreSQL Schema Plan

This document proposes the persistent data model for replacing the in-memory mock API with REST microservices. It is a planning document, not a migration script.

## Goals

- Preserve the current frontend API contracts while introducing durable storage.
- Keep money, order history, and status transitions auditable.
- Support more than one restaurant location from the beginning.
- Allow the services to be split later without redesigning the domain model.
- Avoid storing derived dashboard and bill data as duplicated state.

## Recommended service boundaries

Use separate schemas or databases per service in production. During the first implementation, one PostgreSQL database with these schemas is easier to operate:

| Schema | Service | Owns |
| --- | --- | --- |
| `identity` | Identity service | Restaurants, staff users, roles, sessions |
| `catalog` | Catalog service | Categories, menu items, add-ons, item/add-on links |
| `floor` | Floor service | Dining tables and current table occupancy |
| `ordering` | Order service | Orders, order items, item add-ons, status history |
| `billing` | Billing service | Invoices, invoice lines, payments, tax snapshots |
| `reporting` | Reporting service | Read models and dashboard aggregations |
| `platform` | Shared platform concerns | Outbox events, idempotency keys, audit records |

A service should own writes to its tables. Other services should use REST APIs or events instead of cross-service foreign keys. The foreign keys below are valid for the initial single-database deployment; remove cross-schema foreign keys when the services move to separate databases.

## Entity relationships

```text
restaurants
  |-- staff_users -- user_sessions
  |-- catalog.categories -- menu_items -- menu_item_addons -- addons
  |-- dining_tables
  |-- orders -- order_items -- order_item_addons
  |                 |
  |                 +-- invoices -- invoice_lines -- payments
  |
  +-- audit_events / outbox_events
```

## PostgreSQL conventions

- PostgreSQL 16 or later.
- Use `uuid` primary keys generated by the application or `gen_random_uuid()`.
- Use `timestamptz` for all timestamps. Store the restaurant timezone on `restaurants`.
- Use `numeric(12,2)` for prices, totals, tax, and payments. Never use floating point for money.
- Use `citext` for case-insensitive usernames and restaurant codes, or normalize values in the application.
- Use `jsonb` only for extensible metadata and event payloads, not for core relationships.
- Add `created_at`, `updated_at`, and an optional `deleted_at` to mutable business records.
- Use optimistic concurrency with an integer `version` column on records updated by multiple services.
- Store a UTC timestamp and derive display date/time in the restaurant timezone.

## Core schema

### `identity` schema

#### `identity.restaurants`

| Column | Type | Constraints | Purpose |
| --- | --- | --- | --- |
| `id` | uuid | PK | Restaurant identity |
| `code` | citext | UNIQUE, NOT NULL | Stable tenant code |
| `name` | text | NOT NULL | Current `restaurant.name` |
| `tagline` | text | NOT NULL DEFAULT '' | Branding text |
| `gstin` | text | NOT NULL DEFAULT '' | Tax registration number |
| `address` | text | NOT NULL | Restaurant address |
| `phone` | text | NOT NULL | Contact phone |
| `timezone` | text | NOT NULL DEFAULT 'UTC' | Local display timezone |
| `currency` | char(3) | NOT NULL DEFAULT 'INR' | ISO currency code |
| `tax_rate` | numeric(5,4) | NOT NULL DEFAULT 0.0500 | Current default GST rate |
| `created_at` | timestamptz | NOT NULL | Creation time |
| `updated_at` | timestamptz | NOT NULL | Last update |

Add a check constraint: `tax_rate >= 0 AND tax_rate <= 1`.

### `floor` schema

#### `floor.dining_tables`

| Column | Type | Constraints | Purpose |
| --- | --- | --- | --- |
| `id` | uuid | PK | Table ID |
| `restaurant_id` | uuid | FK, NOT NULL | Tenant owner |
| `number` | text | NOT NULL | T-01, T-02, etc. |
| `capacity` | integer | NOT NULL | Seating capacity |
| `status` | text | NOT NULL DEFAULT 'vacant' | Current table state |
| `current_order_id` | uuid | NULL | Active order, resolved by ordering service |
| `created_at` | timestamptz | NOT NULL | Creation time |

## Status and ownership rules

- Catalog owns menu availability and prices.
- Ordering validates current catalog data but stores immutable item and add-on snapshots.
- Floor owns table status. Ordering requests table occupancy through a floor API or event.
- Billing owns invoices and payments. It must never recalculate old invoices from current menu prices.
- A served order is not automatically a completed/paid order; payment and completion are separate transitions.
- Only identity services read password hashes and session tokens.
- Dashboard statistics are read models built from events or SQL views; they are not hand-edited tables.

## Migration phases

1. **Foundation**: Create schemas, restaurants, staff users, categories, menu items, add-ons, tables, and seed data. Hash the two demo passwords.
2. **Catalog**: Replace menu and add-on mock handlers. Preserve response fields by mapping `is_available` to `available` and counting `menu_item_addons` as `addons`.
3. **Ordering**: Create order, item, add-on snapshot, and status-history tables. Add transactional order creation and table occupancy updates.
4. **Identity**: Replace in-memory UUID sessions with hashed, expiring sessions or an external identity provider.
5. **Billing**: Generate immutable invoice snapshots and payments. Rebuild order history from durable records.
6. **Events and reporting**: Add outbox publishing and dashboard read models after transactional APIs are stable.
7. **Service extraction**: Move schemas into separate databases one service at a time. Replace cross-database foreign keys with IDs plus API/event validation.

## Decisions to confirm before implementation

- Whether the first production version supports multiple restaurants or only one tenant.
- Whether staff authentication will remain local or move to Azure Entra ID/B2C.
- Whether GST rules are fixed at 5% or need jurisdiction-specific tax components.
- Whether an order can move from `served` to `completed` only after payment.
- Whether table reservations need a separate reservation domain.
- Which event broker will carry outbox events: Azure Service Bus, RabbitMQ, or PostgreSQL polling during the first phase.
- Whether invoices require legally controlled numbering and an immutable archive.
